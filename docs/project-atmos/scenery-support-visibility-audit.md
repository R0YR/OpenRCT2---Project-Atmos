# Pacific scenery support visibility audit — 2026-10-21

**Resolved follow-up:** The actual ship boxes and matching road cases contain full-tile support blockers. Wooden scenery supports ignored their segment reservations; `Project-Atmos-blocker-fix.exe` now respects them. See [scenery-support-blockers.md](scenery-support-blockers.md). The investigation below records the earlier diagnostic state.


No production visibility flags or park elements were changed by this investigation.

## Evidence

- Loaded the original `Pacific Ocean Park Vespucci Beach by Royr.sv6`, isolated `artifacts/pacific-repro/pacific.park`, and newest working-profile autosave `autosave_2026-10-20_18-00-37.park` using the native loader.
- All **170,814 element diagnostic signatures** match: tile coordinates, element order/type, base/clearance height, invisibility, object index, scenery support flags/object support policy, and hidden paths at the same height. This checks support-relevant state, not every age/animation byte.
- Pacific contains 5,326 paths, including 78 tile-invisible paths; 63,941 small-scenery elements (5 hidden), 33,083 large-scenery elements (5 hidden). 50,732 small-scenery elements have `needsSupports`, but 63,060 small-scenery objects use `hasNoSupports`; 16,835 large-scenery tiles allow supports. Transparent custom paths are distinct from tile-invisible paths and are not counted as invisible merely because their sprites are blank.
- Five native 1920×1080 views (whole park at all four rotations plus saved close view) produce **zero colour-byte differences** with auxiliary depth/sway/receiver recording on vs off.
- Recompiled original-root `Drawing.Sprite.cpp` as an isolated explicit linker override: **zero colour-byte differences in all five views**. This excludes the recent raw masked depth recording branch as the cause in these views.
- Recompiled `git HEAD:src/openrct2/paint/Paint.cpp` as an isolated explicit linker override: **zero colour-byte differences in all five views**. The new paint metadata does not explain the screenshot geometry.
- Native support painters, tile-element dispatcher and Tile Inspector world logic match the original checkout. The inspector UI change only reads Atmosphere light counts. Atmosphere options/light UI does not call `ViewportSetVisibility`.

## Concrete screenshot location and view flags

The beach pier from the supplied screenshot is reproduced close to tile **(122,75)**, rotation 3. Native normal rendering contains the dark cross-braces beneath the decking. Setting both `ViewportFlag::hideSupports` and `ViewportFlag::invisibleSupports` removes those native braces; the round object posts and decking remain. **1,610 colour pixels** change in the 1920×1080 pier view. This establishes that the pictured braces respond to the native support visibility feature, rather than being generated by the atmosphere shadow pass.

Visual evidence:

- `artifacts/scenery-support-diagnostics/pier-normal.png`
- `artifacts/scenery-support-diagnostics/pier-hidden.png`
- Complete corresponding images: `fixture-raw-5.ppm` / `fixture-hidden-5.ppm`.

`invisible_supports=true` in configuration saves the transparency mode, not the `hideSupports` view flag itself. Native `ViewportSetVisibility(standard)` clears `hideSupports`; scenery, footpath and construction flows already call this in the unchanged source. Loading a park also does not restore this temporary hide flag. These are plausible explanations for supports reappearing after tool use/reload; **a specific historical trigger was not observed and no commit regression is claimed**.

## Regression tests and reproduction

`./scripts/test-scenery-support-visibility.ps1` passes 36 native combinations (four rotations, three heights, normal/translucent/hidden), plus genuine scenery paint presence and disappearance across all rotations and read-only/reversible Inspector operations. Whole element bytes are unchanged by Inspector query and after restoring invisibility.

`./scripts/diagnose-scenery-supports.ps1` writes element CSV and stats. Set `ATMOS_SUPPORT_RENDER=1` for native normal/hidden/aux comparisons, `ATMOS_SUPPORT_OWNERS=1` for native wooden sprite owners. Optional `ATMOS_ORIGINAL_SPRITE=1` and `ATMOS_LEGACY_PAINT=1` build isolated source overrides from the prepared diagnostic copies. None of these runs write a park save.

A complete identification of every individual road-corner sprite owner (path railing vs scenery/ride support) is deferred; the concrete pier visibility result does not require guessing that ownership.

## Additional category proof and limit

Explicitly clearing the entire indexed framebuffer to palette 10 before each native render leaves all auxiliary comparisons and support hide pixel counts unchanged. These are not leftovers from preceding frames.

The dark underwater patch at the upper left of the enlarged pier crop **does not disappear with support hiding alone**. Native category-isolation renders establish that it disappears with scenery hiding, remains with path hiding, and remains with ride hiding. The matching pixel-writer trace records small scenery `1K Ruin` (entry 39) / `Liampie - Underbrush 4` (entry 151), followed by the native water palette filter. This patch is therefore scenery content below water, not evidence that the path bridge support image ignores the support flag. `pier-category-probe.png` contains the four comparison panels.

Do not extrapolate the pier braces result to every dark grid in the supplied street/ship screenshots. The precise sprite owner for those other locations remains unconfirmed. No speculative `Paint.Path.cpp` change was applied.
